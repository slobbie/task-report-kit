# 태스크 구현과 AS-IS/TO-BE 화면 검증

Claude Code(`/task-asis-tobe <태스크>`)와 Codex(`$task-asis-tobe <태스크>`)에서 같이 쓴다. 이 문서의 `<스킬 폴더>`는 이 SKILL.md가 있는 폴더이고, `<작업 폴더>`는 Claude Code의 scratchpad 폴더나 Codex의 임시 폴더처럼 프로젝트 밖의 작업용 폴더다.

태스크 하나를 받아 **코드 수정 전 화면 캡처 → 구현 → 수정 후 화면 캡처 → 검토 → 보고서 → 보고**까지 한 번에 진행한다.
보고서는 실제로 실행한 화면만 담는다. 시안 이미지나 추측한 화면을 넣지 않는다.

## 한국어 작성 기준

한국어를 쓰기 전에 `<스킬 폴더>/references/korean-writing.md`를 읽고 적용한다. 같은 skills 폴더에 `natural-writing-kr` 스킬이 설치되어 있으면 그 `SKILL.md`도 함께 적용한다. 보고서 본문뿐 아니라 항목 설명(`lead`), 캡처 설명(`caption`), 번호 설명, 정리 상자, 마지막 채팅 보고까지 모두 이 기준을 따른다. 단어를 가운뎃점으로 잇지 않는다(예: "개발 환경 · 가상 데이터" 대신 "개발 환경에서 가상 데이터로 확인"). 보고서를 넘기기 전에 `python3 <스킬 폴더>/scripts/audit_report.py <보고서.html>`을 돌리고, 위반이 나오면 manifest를 고쳐 다시 생성한다. 검사를 통과했다고 자연스러운 문장이라는 뜻은 아니므로 문장은 따로 읽어 본다.

## 0. 시작 전에 정할 것

- **태스크 범위**: 요청한 태스크 번호와 이름, 근거 자료(기획서, 정책서, 피그마, 제안서)를 확인한다. 범위가 겹치는 다른 태스크가 있으면 어디까지가 이번 태스크인지 정하고, 범위 밖은 건드리지 않는다.
- **플랫폼**: 모바일 앱이면 iOS와 Android, 웹이면 데스크톱과 모바일 화면 크기를 기본으로 찍는다. 사용자가 다르게 정하면 따른다.
  - 모바일 앱: [references/mobile-app.md](references/mobile-app.md)
  - 웹 서비스: [references/web.md](references/web.md)
- **캡처 순서와 운영 환경**: [references/capture-policy.md](references/capture-policy.md)를 따른다. 개발 환경, 테스트 데이터, 운영 환경(조건 지킴), 캡처 실패 순서로 시도하고, 어떤 경우에도 HTML 보고서는 만든다.
- **테스트 데이터**: 화면을 끝까지 넘기려면 테스트 계정, 번호, 데이터가 필요한지 먼저 본다. 없으면 사용자에게 한 번 묻는다. "없이 진행"이면 캡처할 때만 응답을 바꾸는 임시 코드를 넣고 `TEMP-CAPTURE` 주석을 단 뒤 캡처가 끝나면 반드시 지운다(마지막에 `grep -rn TEMP-CAPTURE`로 확인).
- **실제 외부 호출**: 문자 발송, 결제, 외부 인증처럼 실제 비용이나 부작용이 생기는 화면은 캡처하지 않는다. 그 화면은 "확인하지 못한 것"으로 보고한다.

## 1. 준비

1. 근거 자료에서 이번 태스크가 바꾸는 화면과 동작을 뽑는다. 피그마가 있으면 대상 프레임의 디자인 컨텍스트와 스크린샷을 읽는다.
2. 고칠 코드와 그 코드를 쓰는 곳을 읽는다. 공유 컴포넌트를 바꾸면 다른 경로에 영향이 없는지 확인하고, 다른 태스크 범위의 경로는 기존 동작을 유지하도록 분기한다.
3. 프로젝트 규칙(`AGENTS.md`, `CLAUDE.md`, `.claude/rules/*` 등)을 확인한다. 규칙과 기존 코드 관행이 충돌하면 기존 관행을 따르고 보고 때 한 줄로 알린다.
4. 빌드와 실행을 먼저 시작한다. 오래 걸리는 빌드와 개발 서버는 로그 파일로 출력을 보내며 백그라운드로 돌리고(도구의 백그라운드 실행 기능이나 `nohup ... > log 2>&1 &`), 그동안 코드를 읽는다.

## 2. AS-IS 캡처 (코드 수정 전)

- **기존 파일을 고치기 전에 찍는다.** 새 파일 작성은 화면에 연결하지 않는 한 먼저 해도 된다.
- 바뀌는 흐름을 처음부터 끝까지 찍는다. 없어지는 단계는 모두 남긴다(나중에 다시 찍을 수 없다).
- 펼침, 시트, 팝업처럼 상태가 바뀌는 화면은 상태별로 찍는다.
- 개발 도구 오버레이(Expo 톱니 버튼, 디버그 배너 등)가 찍히면 끄고 다시 찍는다.
- 파일명: `shots/<플랫폼>/asis-<순번>-<내용>.png`

## 3. 구현

- 태스크 범위만 바꾼다. 백엔드나 다른 태스크가 필요한 지점은 개발 빌드에서만 건너뛰게 하고, 릴리즈 빌드에서는 넘어가지 않게 막는다(fail-closed). 임시 처리는 파일 하나에 모으고 주석으로 이유를 적는다.
- 피그마가 있으면 값(크기, 색, 간격, 문구)을 맞추고 기존 공통 컴포넌트와 토큰을 우선 쓴다. 에셋은 피그마에서 받은 원본을 쓴다.
- 프로젝트의 린트와 타입 검사를 통과시킨다. 전체 검사에서 오류가 나면 바꾼 파일의 오류인지, 원래 있던 오류인지 파일 목록으로 구분한다.

## 4. TO-BE 캡처 (코드 수정 후)

- 코드가 실제로 반영됐는지 먼저 확인한다(개발 서버 재번들, 새로고침). 예전 화면이 나오면 캡처하지 말고 원인부터 해결한다.
- AS-IS와 같은 흐름, 같은 데이터로 찍어 나란히 비교할 수 있게 한다.
- 새로 생긴 화면, 다음 단계로 넘어간 화면, 뒤로가기, 링크 열림처럼 **동작**도 직접 실행해서 확인한다.
- 금방 지나가는 화면(로딩 등)은 동작과 동시에 연속 캡처해서 잡는다. 파일 크기나 화면을 보고 맞는 장을 고른다.
- 찍은 화면은 축소본으로 직접 열어 확인한다. 엉뚱한 화면이 찍혔으면 다시 찍는다.
- 피그마가 있으면 새 화면을 시안과 비교한다. 플랫폼 차이(줄바꿈 등)는 보고서 설명에 쓴다.

## 5. 검토

구현한 결과를 근거 자료와 코드에 비춰 스스로 검토한다. 문제가 나오면 고치고 해당 화면을 다시 찍은 뒤 다음 단계로 간다. 고치지 못한 것은 보고 메시지의 "검토 결과"에 남긴다.

- **시안과 정책 대조**: TO-BE 화면을 피그마 프레임과 항목별로 비교한다(문구, 순서, 버튼 상태, 간격, 색). 정책서의 요구사항 ID가 화면과 동작에 모두 반영됐는지 확인한다.
- **범위**: `git diff --stat`과 새 파일 목록을 보고 태스크 범위 밖 파일을 건드렸는지 확인한다. 공유 컴포넌트를 바꿨다면 다른 경로가 기존대로 동작하는지 코드로 확인한다.
- **남은 임시 코드**: `grep -rn TEMP-CAPTURE`, 디버그 출력(`console.log` 등), 하드코딩한 테스트 값이 남지 않았는지 본다.
- **개발 전용 처리**: 개발 빌드에서만 건너뛰는 코드가 릴리즈 빌드에서는 막히는지 조건을 다시 읽는다.
- **예외 동작**: 뒤로가기, 취소, 실패 응답, 빈 값처럼 시안에 없는 경로가 깨지지 않는지 확인한다.

이미 다른 사람이나 다른 도구가 구현한 작업을 검토할 때도 이 스킬을 쓴다. 이때는 기준 브랜치를 별도 작업 트리(`git worktree add`)에서 실행해 AS-IS를 찍고, 작업 브랜치로 TO-BE를 찍은 뒤 이 검토 단계를 진행한다. 사용자가 요청하지 않으면 코드는 고치지 않고 검토 결과만 보고한다.

## 6. 보고서

1. 한국어 작성 기준(`<스킬 폴더>/references/korean-writing.md`)을 다시 확인한다.
2. `<작업 폴더>`에 `manifest.json`을 만들고 생성 스크립트로 HTML을 만든다.
   ```
   python3 <스킬 폴더>/scripts/build_report.py <manifest.json> <출력.html>
   ```
   형식은 [assets/report-template.html](assets/report-template.html)이다. 항목마다 AS-IS와 TO-BE를 두 칸으로 놓는다. 플랫폼들의 항목 구성이 같으면(iOS와 Android가 같은 화면을 다루면) 항목을 한 번만 두고 플랫폼 전환 토글로 캡처와 설명을 바꿔 보여 준다. 같은 내용을 플랫폼별로 두 번 나열해 스크롤을 늘리지 않는다. 플랫폼마다 항목 id와 순서를 맞추면 생성기가 자동으로 토글을 만들고, 플랫폼별로 다른 설명이나 캡처는 토글에 따라 바뀐다. 항목 자체가 플랫폼마다 다를 때만 플랫폼별로 나열한다. manifest 형식은 스크립트 첫머리 주석에 있다. 데스크톱 웹처럼 가로로 긴 캡처는 그 플랫폼에 `"wide": true`를 준다.
3. 항목 구성
   - 항목 하나는 사용자가 알아볼 수 있는 변경 하나다(입력 단계, 옵션 선택 시트, 새 화면, 뒤로가기 동작 등).
   - `lead`는 이 항목의 배경과 무엇이 어떻게 바뀌었는지 문장으로 쓴다. 기능에 꼭 필요한 조건(개발 빌드에서만 건너뛴다 등)은 해당 항목 설명에 쓴다.
   - 항목 문장은 [references/item-writing.md](references/item-writing.md)를 따른다. 쓰기 전에 그 문서의 예시를 읽는다.
   - AS-IS 칸에는 캡처와 함께 이전 동작의 문제(누가 무엇 때문에 어떤 결과를 겪었는지)를, TO-BE 칸에는 캡처와 함께 바뀐 결과와 그래서 해결된 문제를 쓴다. 코드 동작이나 기능 나열로 대신하지 않는다.
   - 한 항목에 변경점이 여럿이면 AS-IS의 ①번 문제와 TO-BE의 ①번 결과가 1:1로 짝이 되게 번호를 붙인다. 캡처에 번호를 달았으면 그 번호 설명이 곧 문제 문장이고, 같은 번호로 글을 다시 쓰지 않는다. 문체는 합니다체로 통일한다.
   - 번호 표시: 화면에 보이는 변경점은 캡처의 해당 위치에 번호 박스를 겹치고 캡처 아래 같은 번호로 설명한다(manifest 이미지 항목의 `marks`). 위치는 손짐작으로 잡지 않는다. 웹은 `web_capture.mjs`의 `shot(라벨, { marks: [{ n, selector, text }] })`로 요소 좌표를 저장해 그 파일 경로를 `marks`에 넘긴다. 앱은 Maestro `hierarchy`의 요소 좌표를 쓰고, 읽히지 않는 요소(바텀시트 등)는 캡처 픽셀을 측정해 잡는다. 생성 후 렌더링을 열어 번호가 제자리에 붙었는지 확인한다.
   - 새 화면이라 AS-IS가 없으면 `{"text": "해당 화면 없음."}`처럼 사실만 적는다.
   - 보고서에 '확인 필요', '미결 사항', '확인하지 못한 사항' 절을 따로 만들지 않는다. 확인하지 못한 것은 보고 메시지에 쓴다.
   - 편집 범위: 항목 설명, 캡션, 번호 설명에 작업 과정("개발 환경에서 화면을 열었다", "임시 코드로 띄웠다")을 쓰지 않는다. 직접 재현한 문제와 테스트하지 않은 동작을 구분하고, 테스트하지 않은 동작을 문제나 개선안으로 쓰지 않는다. 사용자가 지운 내용은 다듬으면서 되살리지 않고, 지적받은 유형은 보고서 전체에서 찾아 함께 고친다. 자세한 기준은 item-writing.md의 '읽는 사람이 한 번에 이해하게 쓴다'를 따른다.
4. headless Chrome으로 렌더링해서 깨짐, 이미지 누락, 레이아웃을 확인한다. 아래는 macOS 경로이고, 다른 OS는 Chrome 실행 파일 경로만 바꾼다.
   ```
   "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --hide-scrollbars --window-size=1280,3200 --screenshot=<png> "file://<html>"
   ```

## 7. 보고

보고 메시지는 아래 순서로 짧게 쓴다. 커밋은 사용자가 요청할 때만 한다.

1. 보고서 경로 (절대경로 링크)
2. 바뀐 것: 화면과 파일
3. 검증: 실행한 기기와 화면, 린트와 타입 검사 결과
4. 검토 결과: 검토에서 찾아 고친 것, 고치지 못한 것
5. 확인하지 못한 것: 무엇을, 왜 못 했는지(시도한 방법과 막힌 지점), 운영 화면을 쓴 항목
6. 따로 알릴 것: 기기 상태를 바꾼 일(앱 재설치, 로그아웃 등), 실행 중으로 남긴 서버, 규칙과 다르게 한 점
7. 다음 태스크 제안 한 줄

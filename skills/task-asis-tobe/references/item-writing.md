# AS-IS / TO-BE 항목 작성법

`task-asis`, `task-asis-tobe`, `task-tobe`가 함께 따른다. 독자가 AS-IS만 읽고 무엇이 문제인지, TO-BE만 읽고 왜 바꾸는지 알 수 있어야 한다.

## AS-IS: 문제를 쓴다

- 번호 하나에 문제 하나를 한두 문장으로 쓴다. **누가, 무엇 때문에, 어떤 결과(피해, 혼란, 위반)를 겪는지**가 들어가야 한다.
- 코드가 어떻게 동작하는지(함수 이름, 조건식, 상태값)로 문제를 대신하지 않는다. 동작은 결과를 이해하는 데 필요한 만큼만 쓰고, 코드 위치 같은 근거는 '근거' 정리 상자로 보낸다.
- 검증 한계("실제 서버 권한은 검증하지 않았다" 등)는 문제 문장에 섞지 않는다. 두 스킬 모두 보고서에는 넣지 않고 마지막 채팅 보고에만 쓴다.
- 기능 설명("쿠폰을 적용하면 결제 금액에서 할인된다")은 AS-IS가 아니라 항목 설명(`lead`)에 쓴다.
- `task-asis-tobe`에서는 이전 동작의 문제, 즉 왜 바꿔야 했는지를 쓴다.

## 읽는 사람이 한 번에 이해하게 쓴다

쉬운 말로 바꾸는 데서 끝내지 않는다. 읽는 사람이 무슨 일이 왜 생겼는지 한 번 읽고 알 수 있어야 한다.

- **확인하는 대상을 구체적으로 쓴다.** "검증"처럼 뭉뚱그리지 말고 "쿠폰 사용 기한 확인"처럼 실제로 무엇을 확인하는지 쓴다. 그 동작이 왜 실패하거나 무시되는지도 같은 문장에서 설명한다.
- **사용자가 화면에서 겪는 일을 바로 쓴다.** "주문이 보이지 않는다"가 아니라 "목록이 최근 50건만 불러오고 다음 페이지가 없어 그 이전 주문을 볼 수 없다"처럼 원인과 화면의 결과를 함께 쓴다.
- **결과는 일어나는 순서대로 쓴다.** 화면에 보이는 결과, 저장할 때 생기는 문제, 다시 열었을 때 보이는 결과 순서로 쓴다.
- **확인한 정도를 구분한다.**
  - 직접 재현한 문제와 아직 테스트하지 않은 동작을 한 문장에 섞지 않는다.
  - 가상 데이터나 임시 코드로만 본 현상은 운영에서도 생기는 버그로 단정하지 않는다.
  - 실행해 보지 못한 동작을 "~할 수 있습니다"로 문제처럼 쓰지 않는다. 문제로 쓸 수 있는 것은 직접 확인한 사실(예: 처리하는 코드가 없음)까지다.
  - 테스트를 더 해야 한다는 이유만으로 TO-BE 개선안을 만들지 않는다. 남은 테스트는 채팅 보고에 쓴다.
- **이미 되는 동작을 먼저 확인한다.** 현재 동작을 확인한 뒤 요구와 무엇이 다른지를 쓴다. 이미 되는 것을 없는 것처럼 쓰지 않는다.
- **작업 과정을 본문에 쓰지 않는다.** "개발 환경에서 화면을 열었다", "임시 코드로 띄웠다", "시작 화면을 캡처했다" 같은 문장은 항목 설명, 캡션, 번호 설명 어디에도 넣지 않는다. 작업 과정과 확인하지 못한 것은 채팅 보고에만 쓴다.
- **지운 내용은 되살리지 않는다.** 사용자가 삭제한 내용은 문장을 다듬는 과정에서 다시 넣지 않는다.
- **지적은 보고서 전체에 적용한다.** 사용자가 한 번호를 지적하면 같은 유형의 문장을 보고서 전체에서 찾아 함께 고친다.

| 나쁜 예 | 고치는 방향 |
| --- | --- |
| 쿠폰 검증이 동작하지 않습니다. | 쿠폰 사용 기한 확인처럼 실제 확인 대상을 쓰고, 장바구니에서만 확인하고 결제 직전에는 다시 확인하지 않는다는 이유를 같은 문장에 씁니다. |
| 일부 주문이 보이지 않습니다. | 다음 페이지가 없어서 최근 50건보다 오래된 주문을 회원이 볼 수 없다고 씁니다. |
| 상품 옵션 선택이 사라집니다. | 화면에서 보이는 결과, 저장할 때 생기는 문제, 다시 열었을 때 보이는 결과를 순서대로 씁니다. 가상 테스트에서만 봤다면 운영 버그로 단정하지 않습니다. |
| TO-BE: 해당 동작을 테스트해 확인합니다. | 테스트하지 않은 동작은 개선안이 아닙니다. 채팅 보고의 확인하지 못한 것에 씁니다. |
| 지역별 배송비를 계산하는 기능이 없습니다. | 이미 되는 동작부터 씁니다. 결제 화면은 제주와 도서산간 배송비를 더하지만, 장바구니의 예상 결제 금액에는 빠져 있다는 차이를 씁니다. |

## TO-BE: 개선과 그 이유를 쓴다

- AS-IS와 같은 번호로 짝을 맞춘다. 번호마다 **바뀐 뒤 상태**와 **그래서 AS-IS 몇 번 문제가 어떻게 사라지는지**를 함께 쓴다.
- "정한다", "검토한다", "반영한다"처럼 할 일만 쓰고 끝내지 않는다. 바뀐 뒤 사용자가 무엇을 보고 겪는지를 쓴다.
- 정책이 정해지지 않았으면 선택지와 추천안을 쓰고 "(결정 필요: …)"로 무엇을 정해야 하는지 밝힌다.
- `task-asis-tobe`에서는 실제로 바뀐 결과와 그 결과로 해결된 문제를 쓴다.

## 번호와 문체

- **번호 하나에 설명 하나**: 캡처에 번호를 달았으면 그 번호 설명(`marks`의 `text`)이 곧 그 번호의 문제 문장이다. 같은 번호로 아래에 글을 다시 쓰지 않는다. 캡처에 번호를 달 수 없는 문제(보내는 값 등)만 `{"text": "① …"}`로 쓴다.
- 문체는 합니다체로 통일한다. 번호 설명, 칸 안의 글, 항목 설명, 정리 상자 모두 같다.

## 예시

나쁜 예

- AS-IS ① 쿠폰 확인 함수는 결제 단계에서 만료일을 다시 확인하지 않아, 다른 조건이 없다면 만료된 쿠폰도 적용되도록 정의돼 있다. 화면 재현만으로 실제 결제 금액을 검증한 것은 아니다.
- TO-BE ① 결제 단계에서 만료 쿠폰을 어떻게 처리할지 정하고, 정한 기준을 서버 조건에 반영한다.

좋은 예

- AS-IS ① 회원이 장바구니에서 쿠폰을 적용한 뒤 쿠폰 사용 기한이 지나서 결제해도, 만료된 쿠폰 할인이 결제 금액에 그대로 남습니다. 운영자는 기한이 끝난 쿠폰만큼 할인된 주문을 받게 됩니다.
- AS-IS ② 결제 완료 화면에는 할인된 금액이 나오지만 주문 내역에는 쿠폰 표시가 없습니다. 회원은 어떤 쿠폰이 쓰였는지 주문 내역에서 확인할 수 없습니다.
- TO-BE ① [결제하기]를 누르는 시점에 서버가 쿠폰 사용 기한을 다시 확인하고, 기한이 지났으면 '쿠폰 사용 기간이 지났어요' 안내와 함께 할인 전 금액을 보여 줍니다. 만료된 쿠폰으로 결제되지 않으므로 ①의 할인 주문이 사라집니다. (결정 필요: 기한 직전에 장바구니에 담은 쿠폰에 유예 시간을 둘지)
- TO-BE ② 주문 내역에 사용한 쿠폰 이름과 할인 금액을 표시합니다. 회원이 주문 내역에서 쿠폰 사용 여부를 바로 확인할 수 있어 ②의 문제가 사라집니다.

나쁜 예에서 빠진 것: 누가 어떤 피해를 보는지(AS-IS), 바뀐 뒤 상태와 해결되는 문제(TO-BE). 검증 한계가 문제 문장에 섞여 있고, TO-BE는 할 일만 있다.

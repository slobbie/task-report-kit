# 작업 전 검토

Claude Code(`/task-plan`)와 Codex(`$task-plan`)에서 같이 쓴다. 캡처 방법과 보고서 도구는 `task-asis-tobe` 스킬의 것을 그대로 쓴다.

- 공통 도구 폴더(`<도구 폴더>`): 이 SKILL.md가 있는 폴더와 같은 skills 폴더 안의 `task-asis-tobe` 폴더(`../task-asis-tobe`). 두 스킬은 함께 설치해야 한다.
  - 모바일 앱 캡처: `references/mobile-app.md`
  - 웹 캡처: `references/web.md`, `scripts/web_capture.mjs`
  - 보고서: `scripts/build_report.py`, `assets/report-template.html`
- `<작업 폴더>`는 Claude Code의 scratchpad 폴더나 Codex의 임시 폴더처럼 프로젝트 밖의 작업용 폴더다.

**결과물은 항상 HTML 보고서다.** 캡처를 못 해도 보고서를 만들고, md 파일이나 채팅 답변으로 대신하지 않는다. 캡처 순서와 운영 환경 사용 기준은 `<도구 폴더>/references/capture-policy.md`를 따른다.

**코드를 고치지 않는다.** 캡처를 위해 임시 코드가 꼭 필요하면 `TEMP-CAPTURE` 주석을 달고, 끝나면 지운 뒤 `grep -rn TEMP-CAPTURE`로 확인한다. 웹은 `page.route()`로 응답을 바꿔 앱 코드를 건드리지 않는다.

## 한국어 작성 기준

한국어를 쓰기 전에 `<도구 폴더>/references/korean-writing.md`를 읽고 적용한다. 같은 skills 폴더에 `natural-writing-kr` 스킬이 설치되어 있으면 그 `SKILL.md`도 함께 적용한다. 보고서 본문뿐 아니라 항목 설명(`lead`), 캡처 설명(`caption`), 번호 설명, 정리 상자, 마지막 채팅 보고까지 모두 이 기준을 따른다. 단어를 가운뎃점으로 잇지 않는다(예: "개발 환경 · 가상 데이터" 대신 "개발 환경에서 가상 데이터로 확인"). 보고서를 넘기기 전에 `python3 <도구 폴더>/scripts/audit_report.py <보고서.html>`을 돌리고, 위반이 나오면 manifest를 고쳐 다시 생성한다. 검사를 통과했다고 자연스러운 문장이라는 뜻은 아니므로 문장은 따로 읽어 본다.

## 검토 기준이 되는 입력

요청에 들어온 것을 기준으로 삼는다. 여러 개가 함께 오면 모두 반영한다.

1. **자료**: 기획서, 정책서, 제안서, 메일, 회의록 등 사용자가 준 자료. 자료에 적힌 요구를 현재 화면과 코드에 비춰 확인한다.
2. **피그마**: 링크나 프레임이 있으면 시안과 현재 화면을 비교한다. 피그마가 없으면 이 비교는 하지 않는다.
3. **개선 요구 사항**: 사용자가 직접 말한 개선 요구. 무엇을 원하는지 파악해서 1과 같은 방식으로 정리한다. 요구가 모호해서 결과가 크게 달라지면 시작 전에 한 번만 묻고, 사소하면 가정을 밝히고 진행한다.

## 1. 자료와 요구 파악

1. 입력에서 요구 항목을 하나씩 뽑는다. 항목마다 출처(자료 이름과 위치, 정책 ID, 피그마 화면 ID, 사용자 요청 문장)를 기록한다.
2. 각 항목이 닿는 현재 화면, 코드 파일, 흐름, API를 찾는다.
3. 자료끼리 내용이 다르면(예: 정책서와 피그마가 다름) 기록해 둔다. 어느 쪽이 맞는지 판단할 근거가 없으면 판단하지 않는다.

## 2. 현재 화면 캡처

- `task-asis-tobe`의 AS-IS 캡처와 같은 방법으로, 요구 항목이 닿는 현재 화면을 찍는다. **모든 항목의 AS-IS에는 실제 화면 캡처가 들어간다.** 캡처 순서(개발 환경, 테스트 데이터, 운영 환경, 캡처 실패)는 capture-policy.md를 따른다. 글만 있는 AS-IS는 그 순서를 모두 시도하고 실패한 경우에만 쓰고, "캡처하지 못함: <이유>"를 함께 적는다.
- 보내는 값이나 저장 방식처럼 화면에 직접 보이지 않는 요구도, 그 동작이 일어나는 화면을 캡처한다(예: 요청 값이 바뀌는 요구라면 그 요청을 보내는 화면). 코드 동작 설명은 캡처 아래 글로 붙인다.
- 새로 생기는 화면처럼 현재 화면이 아예 없으면, 그 화면으로 들어가기 직전 화면을 캡처하고 "해당 화면 없음"이라고 적는다.
- 피그마가 있으면 같은 단계의 프레임 스크린샷도 받아 둔다.

## 3. 항목 정리

항목마다 아래처럼 나눠 적는다.

항목 문장은 `<도구 폴더>/references/item-writing.md`를 따른다. 쓰기 전에 그 문서의 예시를 읽는다.

- **AS-IS는 문제를 쓴다**: 현재 화면 캡처(필수)와 함께, 번호마다 누가 무엇 때문에 어떤 결과(피해, 혼란, 위반)를 겪는지 쓴다. 코드 동작으로 문제를 대신하지 않고, 검증 한계를 섞지 않는다.
- **TO-BE는 개선과 이유를 쓴다**: 같은 번호로 바뀐 뒤 상태와, 그래서 AS-IS 몇 번 문제가 어떻게 사라지는지를 쓴다. "정한다", "반영한다"로 끝내지 않는다. 정책 결정이 필요하면 선택지와 추천안을 쓴다. 피그마가 있으면 시안 이미지를 함께 놓는다.
- **번호 하나에 설명 하나**: 캡처 번호 설명이 그 번호의 문제 문장이다. 같은 번호로 글을 다시 쓰지 않는다.
- **배경은 위로, 한계는 따로**: 기능 설명은 항목 설명(`lead`)에 쓴다. 검증 한계와 확인하지 못한 사항은 보고서에 넣지 않고 마지막 채팅 보고에만 쓴다. 문체는 합니다체로 통일한다.
- **편집 범위**: 항목 설명, 캡션, 번호 설명에 작업 과정("개발 환경에서 화면을 열었다", "임시 코드로 띄웠다", "시작 화면을 캡처했다")을 쓰지 않는다. 직접 확인한 문제와 실행해 보지 못한 동작을 구분하고, 실행해 보지 못한 동작을 "~할 수 있습니다"로 문제처럼 쓰거나 테스트가 더 필요하다는 이유로 개선안을 만들지 않는다. 이미 되는 동작을 먼저 확인하고 차이를 쓴다. 사용자가 지운 내용은 다듬으면서 되살리지 않고, 지적받은 유형은 보고서 전체에서 찾아 함께 고친다. 자세한 기준은 item-writing.md의 '읽는 사람이 한 번에 이해하게 쓴다'를 따른다.
- **근거**: 출처
- **필요한 것**: 프론트만으로 되는지, 백엔드 API나 정책 결정이 필요한지

자료에 있지만 현재 화면과 코드가 이미 그렇게 되어 있으면 "변경 없음"으로 적는다. 요구를 반영할 수 없거나 다른 요구와 충돌하면 그 이유를 적는다.

마지막에 태스크 목록을 만든다. 공수 기준 자료가 있으면 그 항목과 맞추고, 번호를 매핑한 경우 추정인지 근거가 있는지 밝힌다. 백엔드 없이 먼저 할 수 있는 일과 기다려야 하는 일을 나눈다.

## 4. 보고서

1. 한국어 작성 기준(`<도구 폴더>/references/korean-writing.md`)을 다시 확인한다.
2. manifest를 만들고 생성한다. 칸 이름은 기본값(AS-IS, TO-BE)을 쓴다.
   ```
   python3 <도구 폴더>/scripts/build_report.py <manifest.json> <출력.html>
   ```
   - AS-IS 칸: 현재 화면 캡처(`{"img": ...}`, 필수). 화면에 보이는 문제는 캡처의 `marks`에 번호와 문제 문장을 넣고, 캡처에 표시할 수 없는 문제만 `{"text": "① ..."}`로 쓴다. 캡처에 실패한 항목은 `{"text": "캡처하지 못함: <이유>"}`와 코드로 확인한 현재 동작을 넣는다.
   - TO-BE 칸: AS-IS와 같은 번호를 붙인 개선(`{"text": "① ..."}` 또는 시안 이미지의 `marks`). 바뀐 뒤 상태와 해결되는 문제를 함께 쓴다.
   - `lead`: 이 항목의 배경(현재 기능), 요구, 근거를 한두 문장으로 쓴다.
   - 번호 표시: 화면에 보이는 변경점은 캡처의 해당 위치에 번호 박스를 겹치고 캡처 아래 같은 번호로 설명한다(manifest 이미지 항목의 `marks`). 위치는 손짐작으로 잡지 않는다. 웹은 `<도구 폴더>/scripts/web_capture.mjs`의 `shot(라벨, { marks: [{ n, selector, text }] })`로 요소 좌표를 저장해 그 파일 경로를 `marks`에 넘긴다. 앱은 Maestro `hierarchy`의 요소 좌표를 쓰고, 읽히지 않는 요소(바텀시트 등)는 캡처 픽셀을 측정해 잡는다. 생성 후 렌더링을 열어 번호가 제자리에 붙었는지 확인한다.
   - 이 보고서는 바꿀 점을 찾는 것이 목적이므로, 자료끼리 다른 곳, 태스크 목록, 근거(코드 위치, 자료 위치)를 정리 상자(`notes`)로 넣는다. '확인하지 못한 사항' 상자는 만들지 않는다.
3. headless Chrome으로 렌더링을 확인한다.

## 5. 보고

2. 바꿔야 할 항목 요약

5. 확인하지 못한 것: 찍지 못한 화면, 시도한 방법과 막힌 이유, 운영 화면을 쓴 항목
6. 시작할 태스크 제안 한 줄 (구현은 `task-asis-tobe`로 진행)
